# smi2assF 디자인 개선 및 다크모드 설계안

상태: 검토용 계획. 앱 코드에 적용하기 전의 제안이다.

## 1. 현재 화면과 목표

첨부 화면은 안내문이 굵고 크게 보이고, `groove` 테두리는 빛과 그림자 때문에 드롭 영역의 경계를 불균일하게 보이게 한다. 변환 결과도 동일한 굵은 라벨에 길게 출력되는 구조다.

현재 로컬 코드는 기본 창 `400×280`, 최소 창 `320×260`으로 이미 축소되어 있다. 첨부 이미지의 픽셀 크기를 창의 논리 크기로 사용하지 않는다. 이 크기를 기준으로 드롭 영역과 하단 덮어쓰기 옵션의 시각적 완성도를 높인다.

### 필수 조건

- 기본 창 `400×280`, 최소 창 `320×260`을 유지한다. 고배율 글꼴에서 공간이 부족하면 실제 요청 크기에 맞춰 최소 크기만 늘린다.
- 조작 요소는 드롭 영역과 `기존 ASS 파일 덮어쓰기` 체크박스다.
- 드롭하면 즉시 변환하는 동작을 유지한다.
- 기기 언어가 한국어이면 한국어, 나머지는 영어를 표시한다.
- 라이트·다크모드는 운영체제 설정을 자동으로 따른다.
- 기존 Tkinter/ttk, tkinterdnd2, PyInstaller, Inno Setup 구성을 사용한다.
- Windows 빌드는 Python 3.13/Tcl 8.6을 유지한다.
- 현재 브랜치에서 로컬 작업을 수행한다. 커밋·푸시는 사용자의 명시적 요청이 있을 때 수행한다.

## 2. 화면 구성

```text
┌─ OS 기본 제목 표시줄 ──────────────────┐
│                                       │
│  ┌─────────────────────────────────┐  │
│  │                                 │  │
│  │          [파일 → ASS]           │  │
│  │   .smi 파일을 여기에 놓으세요    │  │
│  │      폴더도 넣을 수 있어요       │  │
│  │                                 │  │
│  └─────────────────────────────────┘  │
│  ☐ 기존 ASS 파일 덮어쓰기             │
└───────────────────────────────────────┘
```

| 요소 | 제안 |
|---|---|
| 외곽 여백 | 16 Tk 화면 단위, 배율에 맞춰 조정 |
| 드롭 영역 | 사방이 균일한 1단위 테두리, 평평한 표면, 내부 여백 16 |
| 아이콘 | 28단위 크기의 파일·화살표 선형 아이콘, Canvas로 그려 테마 색 적용 |
| 안내문 | OS 기본 글꼴 14pt, 보통 굵기, 가운데 정렬 |
| 보조문·결과 | OS 기본 글꼴 11pt, 보조 색상, 실제 가용 폭에 맞춰 줄바꿈 |
| 체크박스 | 드롭 영역 왼쪽 가장자리에 정렬, 위 간격 8, OS 기본 글꼴 |
| 제목 표시줄 | 운영체제 기본 창 장식 사용 |

한국어 안내는 `.smi 파일을 여기에 놓으세요` / `폴더도 넣을 수 있어요`, 영어는 `Drop .smi files here` / `Folders work too.`로 제안한다. 확장자의 대소문자 지원은 기존 동작을 유지한다.

### 색상 기준

아래 값은 일반 모드의 기준값이다. macOS의 기본 체크박스와 Windows 고대비 모드는 운영체제 의미 색상을 우선한다.

| 역할 | 라이트 | 다크 |
|---|---|---|
| 창 배경 | `#F6F7F9` | `#181B20` |
| 드롭 표면 | `#FFFFFF` | `#22262D` |
| 주요 텍스트 | `#20252B` | `#EEF1F5` |
| 보조 텍스트 | `#68717D` | `#A7B0BC` |
| 기본 테두리 | `#D8DDE5` | `#3A414C` |
| 드래그·포커스 강조 | `#2F6FEB` | `#6FA8FF` |

일반 텍스트 대비는 4.5:1 이상, 조작 요소의 포커스·선택 표시 대비는 3:1 이상을 검증한다. 기본 드롭 테두리는 장식이며, 드래그 가능 여부는 안내문으로도 전달한다.

## 3. 상태별 표현

| 상태 | 드롭 영역 | 하단 옵션 |
|---|---|---|
| 대기 | 아이콘 + 안내문 + 폴더 안내 | 활성 |
| 파일 드래그 진입 | 강조 테두리 + `놓으면 변환합니다` / `Drop to convert` | 기존 값 유지 |
| 드래그 이탈 | 진입 전 상태로 복귀 | 기존 값 유지 |
| 변환 중 | `변환 중…` / `Converting…` + 대상 파일 수 | 비활성 |
| 완료 | `변환 완료` / `Conversion complete` + 결과 요약 | 활성 |
| 일부 실패 | `일부 파일 변환 실패` / `Some files could not be converted` + 결과 요약 | 활성 |
| 파일 없음·읽기 실패 | 짧은 원인 안내 + 다시 드롭할 수 있다는 안내 | 활성 |

완료 요약은 `대상`, `생성 ASS`, `기존 ASS 유지`, `변환 오류`, `읽기 실패`의 다섯 수치를 모두 유지한다. 예: `대상 12 · 생성 10 · 유지 2` / `오류 0 · 읽기 실패 0`. 최소 크기에서는 보조문을 최대 3줄로 배치한다. 파일 수와 생성 ASS 수는 서로 다른 지표이므로 혼동하지 않는다.

현재 변환 작업은 최종 결과만 전달하므로 진행률 대신 처리 중 문구를 표시한다. 변환 중 추가 드롭·테마 변경에도 현재 작업과 체크박스 값이 유지되어야 한다.

## 4. 다크모드 지원 방식

### macOS

로컬 런타임을 직접 확인한 결과 Tcl/Tk `9.1.0`, 기본 `aqua` 테마, 창 속성 `-appearance auto`를 제공한다. 반면 예전 `tk::unsupported::MacWindowStyle` 명령은 존재하지 않았다. 문서의 예제를 그대로 복사하면 시작 오류가 생길 수 있다.

- 실행 시 지원 속성을 조회하고 `-appearance auto`를 우선 사용한다.
- 이전 런타임에서는 해당 명령의 존재를 확인한 뒤 구형 appearance 경로를 사용한다.
- 첫 실행의 실제 모드는 Tk의 동적 `systemWindowBackgroundColor` RGB를 읽어 판별하는 방식을 먼저 검증한다. 기본 밝기와 다크 밝기를 모두 확인한 뒤 사용자 정의 팔레트에 연결한다.
- Tk 9의 `<<LightAqua>>`, `<<DarkAqua>>` 이벤트로 실행 중 변화를 반영한다. 시작 시 이벤트가 오기를 기다리지 않는다.
- `aqua` 체크박스의 네이티브 선택·비활성·포커스 표현을 유지하고, 주변 배경 및 안내문 색상을 함께 갱신한다.
- 현재 `.app` Info.plist에는 `NSRequiresAquaSystemAppearance` 강제 라이트 설정이 없다. 실제 패키지에서 문제가 확인될 경우에만 번들 설정을 조정한다.

Tk 공식 문서는 macOS 의미 색상과 테마 변경 이벤트를 설명한다. `wm -appearance auto`의 macOS 동작도 공식 정의되어 있다. 다만 문서와 실제 런타임의 제공 명령이 다르므로 기능 탐지가 필요하다. [Tk macOS 설명](https://raw.githubusercontent.com/tcltk/tk/main/macosx/README), [Tk wm 명세](https://raw.githubusercontent.com/tcltk/tk/main/doc/wm.n)

### Windows

- `winreg`로 사용자 앱 색상 설정 `AppsUseLightTheme`를 읽는다. 설정 키 부재·접근 실패 시 일반 라이트 모드로 시작한다. 이 레지스트리 경로는 호환성을 검증해야 하는 구현 의존점이다.
- Tk 8.6에서는 `clam`의 앱 전용 ttk 스타일로 배경·글자·선택·비활성·포커스 색상을 제어한다. 다른 플랫폼에 일괄 적용하지 않는다.
- `ctypes`를 통한 Windows 11의 공식 DWM 옵션으로 네이티브 제목 표시줄을 지원한다. 핸들 생성 뒤 호출하고, 잘못된 핸들·실패 반환값을 안전하게 처리한다.
- Windows 10에서는 앱 내부 다크모드를 제공하며, 공식 지원이 없는 제목 표시줄 다크 처리는 OS 기본 표시로 둔다.
- Windows 고대비 설정을 `SystemParametersInfoW`로 확인하고 고대비가 켜져 있으면 시스템 색상을 우선한다.
- 네이티브 메시지 창은 OS/Tk가 제공하는 표시를 사용한다. 앱 내부 팔레트만으로 모든 네이티브 대화상자 색상을 바꿀 수 있다고 가정하지 않는다.

공식 `DWMWA_USE_IMMERSIVE_DARK_MODE` 지원 기준은 Windows 11 Build 22000부터다. Windows의 시스템 색상과 앱 색상이 서로 다른 설정도 확인한다. [Microsoft DWM 명세](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)

### 변경 감지와 종료

macOS는 지원하는 이벤트를 우선하며, Windows와 구형 macOS는 포커스 복귀 시 재확인하고 Tk `after(2000, ...)`로 보완한다. OS 조회는 메인 스레드에서 빠른 API로 수행하고, 색상 변경이 있을 때만 화면을 갱신한다. 중복 타이머를 만들지 않고 종료·스모크 테스트 때 취소한다. 설정 감지 실패가 앱 실행·변환 실패로 이어져서는 안 된다.

## 5. 예상 변수 및 대응

| 변수 | 대응·확인 |
|---|---|
| 로컬과 배포 런타임의 Tk 차이 | 버전·윈도 시스템·기능을 패키지 로그에 기록하고 지원 여부로 분기 |
| 네이티브 ttk가 지정 색상을 무시 | macOS 네이티브 컨트롤, Windows 제어 가능한 스타일을 각각 확인 |
| 긴 영어 문구·다섯 자리 집계·고배율 | 실제 텍스트 폭에 맞춰 줄바꿈, 옵션 영역 우선 확보 |
| 자식 아이콘·라벨이 드롭을 가로챔 | 실제 파일을 모든 하위 표면에 드롭해 한 번만 변환되는지 확인 |
| 드래그 이탈·변환 중 테마 변경 | 상태와 데이터는 유지하고 색상만 갱신 |
| 고대비·비활성·키보드 포커스 | 색상 외 문구·선택 상태를 유지하고 Tab/Space 동작 확인 |
| 타이머·창 핸들 수명 | 종료 뒤 재호출 없음, 스모크 테스트가 유한 시간 안에 종료 |
| 패키징 재발 | Windows Python/Tcl 고정, sys capture·설치 인자 처리·타임아웃·외부 진단 로그 유지 |

## 6. 완료 기준

1. 한국어·영어 × 라이트·다크 × 기본·최소 크기의 8개 조합에서 모든 문구와 옵션이 잘 보인다.
2. macOS Retina 및 Windows 100/150/200% 배율에서 텍스트와 체크박스가 잘리지 않는다. 높은 배율에서는 필요한 최소 크기 증가를 허용한다.
3. 실행 중 OS 테마를 바꾸면 대기 및 변환 중 화면이 재시작 없이 갱신된다. Windows 보완 조회는 2초 이내에 반영한다.
4. 파일·폴더·여러 파일·공백/한글 경로·기존 ASS·읽기 실패·부분 실패가 기존 변환 규칙대로 처리된다.
5. 기존 전체 테스트와 신규 테마/레이아웃 테스트가 통과하고, macOS 실제 `.app`/DMG 및 Windows 설치 파일의 설치→실행→제거까지 검증한다.
6. 자동 스모크 결과와 실제 육안 확인을 별도로 기록한다. 창 생성 성공만으로 색상이나 드래그 동작을 검증했다고 판단하지 않는다.
